# 短链接服务 API 接口需求文档

文档版本：`v1.0`  
适用项目：Go 结业考核短链接服务  
文档目的：统一后端接口行为，保证前端可以直接按照本文档完成开发和联调。

本文档是前后端共同遵守的接口契约。后端可以使用 Gin、Echo、Fiber 或 Go 标准库实现，也可以使用 GORM 或其他持久化方式，但对外暴露的接口、字段、状态码和业务规则必须符合本文档。

---

## 1. 项目范围

系统是一个带用户系统的短链接服务，用户可以：

- 注册和登录；
- 查看自己的登录信息；
- 创建短链接；
- 查看自己的短链接列表和详情；
- 删除自己的短链接；
- 访问短链接并跳转到原始 URL；
- 查看短链接的点击次数；
- 受到每日创建数量限制。

基础版本不要求实现 API Key、细粒度限流、短链接过期、自定义短码和统计报表。这些功能属于扩展功能，不能影响基础接口的正常使用。

---

## 2. 基本约定

### 2.1 服务地址

本地开发时，后端默认运行在：

```text
http://localhost:8080
```

实际地址必须通过配置修改，前端不能把地址写死在多个页面中。

### 2.2 API 前缀

所有管理接口统一使用以下前缀：

```text
/api/v1
```

公开短链接跳转接口不使用 API 前缀：

```text
/r/:code
```

例如：

```text
管理接口：http://localhost:8080/api/v1/links
跳转地址：http://localhost:8080/r/a1B2c3
```

### 2.3 内容类型

所有带 JSON 请求体的接口必须使用：

```http
Content-Type: application/json
```

JSON 响应统一使用：

```http
Content-Type: application/json; charset=utf-8
```

### 2.4 字段命名

JSON 字段统一使用 `snake_case`，例如：

```json
{
  "original_url": "https://go.dev",
  "click_count": 3,
  "created_at": "2026-09-20T12:00:00Z"
}
```

### 2.5 时间格式

所有时间字段使用 RFC3339 格式，例如：

```text
2026-09-20T12:00:00Z
```

后端可以按照配置的时区计算每日配额，但 API 返回的时间必须使用明确的时区信息。

## 3. 接口总览

| 功能 | 方法 | 路径 | 是否需要登录 |
|---|---|---|---|
| 健康检查 | `GET` | `/health` | 否 |
| 用户注册 | `POST` | `/api/v1/auth/register` | 否 |
| 用户登录 | `POST` | `/api/v1/auth/login` | 否 |
| 当前用户信息 | `GET` | `/api/v1/me` | 是 |
| 创建短链接 | `POST` | `/api/v1/links` | 是 |
| 获取我的短链接列表 | `GET` | `/api/v1/links` | 是 |
| 获取短链接详情 | `GET` | `/api/v1/links/:id` | 是 |
| 删除短链接 | `DELETE` | `/api/v1/links/:id` | 是 |
| 访问短链接 | `GET` | `/r/:code` | 否 |

## 4. 统一响应格式

### 4.1 成功响应

每个接口按照本文档中的示例返回数据。成功响应不要求额外包裹 `data` 字段，避免前端多一层判断。

### 4.2 错误响应

所有错误响应统一使用以下格式：

```json
{
  "code": "INVALID_REQUEST",
  "message": "请求参数不合法"
}
```

`code` 用于前端程序判断，`message` 用于向用户展示或记录日志。后端不应只返回一段纯文本错误。

允许增加 `details` 字段返回字段级错误：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "请求参数校验失败",
  "details": {
    "url": "必须是 http 或 https 地址"
  }
}
```

### 4.3 通用状态码

| 状态码 | 使用场景 |
|---:|---|
| `200 OK` | 查询、登录或删除成功 |
| `201 Created` | 注册或创建短链接成功 |
| `302 Found` | 短链接跳转 |
| `400 Bad Request` | JSON 格式错误或参数校验失败 |
| `401 Unauthorized` | 未登录、token 缺失或 token 无效 |
| `404 Not Found` | 资源不存在，或资源不属于当前用户 |
| `409 Conflict` | 用户名已存在 |
| `429 Too Many Requests` | 超过每日创建配额 |
| `500 Internal Server Error` | 未预期的服务器错误 |

对于其他用户拥有的短链接，详情和删除接口统一返回 `404`，不要返回 `403` 暴露资源存在性。

## 5. 鉴权规则

### 5.1 Token 传递方式

登录成功后，前端保存返回的 token，并在需要登录的接口中发送：

```http
Authorization: Bearer <token>
```

例如：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

token 不允许通过 URL 查询参数传递，也不允许写死在前端代码或后端代码中。

### 5.2 Token 实现方式

后端可以选择以下任一种实现：

- JWT；
- 随机 token 加数据库会话记录。

两种方式对前端的行为必须一致：前端只保存 token 并作为 Bearer token 发送，不解析 token 内容。

token 必须有有效期，默认有效期建议为 24 小时，实际值通过配置修改。

### 5.3 未登录请求

以下情况必须返回 `401`：

- 没有 `Authorization` 请求头；
- Authorization 格式不是 `Bearer <token>`；
- token 不存在；
- token 已过期；
- token 签名或数据库校验失败。

错误示例：

```json
{
  "code": "UNAUTHORIZED",
  "message": "请先登录"
}
```

### 5.4 数据隔离

所有需要登录的短链接查询都必须根据当前 token 对应的用户 ID 过滤。

用户 A 不得通过修改 URL 中的 ID 查看、删除或修改用户 B 的短链接。对于用户 B 的资源，接口返回 `404`。

## 6. 接口详细定义

### 6.1 健康检查

### `GET /health`

用于前端、测试脚本或开发者确认服务是否已经启动。

成功响应：`200 OK`

```json
{
  "status": "ok"
}
```

如果数据库不可用，后端应返回 `500`，而不是始终返回成功。

---

### 6.2 用户注册

### `POST /api/v1/auth/register`

请求体：

```json
{
  "username": "tom",
  "password": "123456"
}
```

字段要求：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `username` | string | 是 | 3 到 32 个字符，建议只允许字母、数字和下划线 |
| `password` | string | 是 | 6 到 72 个字符，不返回到响应中 |

成功响应：`201 Created`

```json
{
  "id": 1,
  "username": "tom"
}
```

业务规则：

- 用户名必须唯一；
- 用户名重复返回 `409`；
- 密码必须使用 bcrypt 等安全哈希算法保存；
- 数据库中不能保存密码明文；
- 注册接口不自动返回登录 token，前端注册成功后跳转到登录页。

用户名重复响应：

```json
{
  "code": "USERNAME_EXISTS",
  "message": "用户名已存在"
}
```

---

### 6.3 用户登录

### `POST /api/v1/auth/login`

请求体：

```json
{
  "username": "tom",
  "password": "123456"
}
```

成功响应：`200 OK`

```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "expires_at": "2026-09-21T12:00:00Z",
  "user": {
    "id": 1,
    "username": "tom"
  }
}
```

登录失败统一返回 `401`，不要区分“用户名不存在”和“密码错误”，避免泄露用户信息：

```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "用户名或密码错误"
}
```

---

### 6.4 获取当前用户信息

### `GET /api/v1/me`

请求头：

```http
Authorization: Bearer <token>
```

成功响应：`200 OK`

```json
{
  "id": 1,
  "username": "tom"
}
```

前端可以在刷新页面后调用此接口确认 token 是否仍然有效。

---

### 6.5 创建短链接

### `POST /api/v1/links`

请求头：

```http
Authorization: Bearer <token>
Content-Type: application/json
```

请求体：

```json
{
  "url": "https://go.dev"
}
```

成功响应：`201 Created`

```json
{
  "id": 1,
  "code": "a1B2c3",
  "original_url": "https://go.dev",
  "short_url": "http://localhost:8080/r/a1B2c3",
  "click_count": 0,
  "created_at": "2026-09-20T12:00:00Z"
}
```

字段要求：

| 字段 | 类型 | 规则 |
|---|---|---|
| `url` | string | 必填，只允许 `http://` 或 `https://` |

业务规则：

- 必须登录；
- URL 不能为空；
- 不允许 `javascript:`、`data:`、`file:` 等协议；
- 后端生成唯一短码；
- 短码冲突时必须重新生成，不能覆盖已有数据；
- 成功创建才计入每日配额；
- 参数错误、鉴权失败和数据库保存失败不计入每日配额；
- `short_url` 必须由后端根据 `PUBLIC_BASE_URL` 配置生成，不能让前端自己拼接。

URL 不合法响应：

```http
400 Bad Request
```

```json
{
  "code": "INVALID_URL",
  "message": "URL 必须使用 http 或 https 协议"
}
```

超过每日配额响应：

```http
429 Too Many Requests
```

```json
{
  "code": "DAILY_QUOTA_EXCEEDED",
  "message": "今日创建次数已达上限"
}
```

---

### 6.6 获取我的短链接列表

### `GET /api/v1/links`

请求头：

```http
Authorization: Bearer <token>
```

支持分页参数：

```text
GET /api/v1/links?page=1&page_size=20
```

参数规则：

| 参数 | 类型 | 默认值 | 规则 |
|---|---|---:|---|
| `page` | integer | `1` | 大于等于 1 |
| `page_size` | integer | `20` | 1 到 100 |

成功响应：`200 OK`

```json
{
  "items": [
    {
      "id": 1,
      "code": "a1B2c3",
      "original_url": "https://go.dev",
      "short_url": "http://localhost:8080/r/a1B2c3",
      "click_count": 3,
      "created_at": "2026-09-20T12:00:00Z"
    }
  ],
  "page": 1,
  "page_size": 20,
  "total": 1
}
```

规则：

- 只能返回当前用户创建的短链接；
- 默认按照创建时间倒序排列；
- 没有数据时 `items` 必须返回空数组 `[]`，不能返回 `null`。

---

### 6.7 获取短链接详情

### `GET /api/v1/links/:id`

请求示例：

```text
GET /api/v1/links/1
```

请求头：

```http
Authorization: Bearer <token>
```

成功响应：`200 OK`

响应结构与列表中的单条数据一致：

```json
{
  "id": 1,
  "code": "a1B2c3",
  "original_url": "https://go.dev",
  "short_url": "http://localhost:8080/r/a1B2c3",
  "click_count": 3,
  "created_at": "2026-09-20T12:00:00Z"
}
```

资源不存在或不属于当前用户时返回：

```http
404 Not Found
```

---

### 6.8 删除短链接

### `DELETE /api/v1/links/:id`

请求头：

```http
Authorization: Bearer <token>
```

成功响应：`200 OK`

```json
{
  "message": "删除成功"
}
```

也可以返回 `204 No Content`，但同一个项目必须保持一致。为了方便前端处理，推荐使用上面的 `200` JSON 响应。

业务规则：

- 用户只能删除自己的短链接；
- 删除后访问原短码必须返回 `404`；
- 删除不会恢复当天已经使用的创建配额；
- 删除不存在或不属于当前用户的短链接返回 `404`。

---

### 6.9 访问短链接

### `GET /r/:code`

该接口不需要登录，用于真实访问短链接。

成功响应：

```http
302 Found
Location: https://go.dev
```

业务规则：

- 短码存在时返回 `302`；
- 响应必须包含正确的 `Location` 请求头；
- 跳转成功前后，点击数必须增加 1；
- 短码不存在或已删除时返回 `404`；
- 该接口不能要求登录；
- 点击数更新失败时，不能把用户跳转到错误地址，后端应记录错误并按项目约定处理。

前端不要使用 `fetch()` 把这个接口当作普通 JSON 接口调用。访问按钮应使用链接或页面跳转：

```javascript
window.location.href = shortUrl;
```

或者：

```html
<a href="http://localhost:8080/r/a1B2c3">访问短链接</a>
```

## 7. 每日配额规则

每日配额由配置项 `DAILY_LINK_QUOTA` 控制。

默认值建议为：

```text
DAILY_LINK_QUOTA=5
```

规则如下：

1. 每个用户单独计算配额，用户之间互不影响。
2. 每天最多成功创建 `N` 条短链接。
3. 每日边界使用 `TIMEZONE` 配置的时区计算。
4. 只有成功保存的短链接才计入配额。
5. 参数错误、未登录、URL 不合法和数据库保存失败不计入配额。
6. 删除短链接不会恢复当天已使用的配额。
7. 超过配额必须返回 `429` 和 `DAILY_QUOTA_EXCEEDED`。
8. 配额不能只在前端判断，后端必须再次校验。
9. 配额检查和创建操作应尽量保证一致性，不能通过快速连续请求轻易绕过。

验收时将 `DAILY_LINK_QUOTA` 设置为 `2`，同一个用户成功创建第 3 条短链接时必须被拒绝。

## 8. 配置要求

所有关键参数必须通过环境变量或配置文件提供，不得硬编码在业务代码中。

建议支持以下配置：

| 配置项 | 示例 | 说明 |
|---|---|---|
| `SERVER_PORT` | `8080` | HTTP 服务端口 |
| `DB_DRIVER` | `sqlite` | 数据库类型 |
| `DB_DSN` | `./data/app.db` | 数据库连接信息 |
| `DAILY_LINK_QUOTA` | `5` | 每个用户每天最多创建数量 |
| `TOKEN_TTL` | `24h` | token 有效期 |
| `PUBLIC_BASE_URL` | `http://localhost:8080` | 生成短链接时使用的公开地址 |
| `CORS_ORIGINS` | `http://localhost:5173` | 允许访问后端的前端地址 |
| `TIMEZONE` | `Asia/Shanghai` | 每日配额计算时区 |
| `JWT_SECRET` | 通过环境变量提供 | 使用 JWT 时必须配置 |

要求：

- `JWT_SECRET`、数据库密码和 API Key 等敏感信息不得提交到 Git；
- 应提供 `.env.example`，但其中只能放示例值；
- 数据库文件所在目录不存在时，程序应能给出清晰错误或自动创建目录；
- 修改每日配额后，重启服务即可生效；
- 程序启动失败时应返回清晰日志，不应静默运行。

---

## 9. CORS 要求

为了支持独立运行的前端，后端必须支持配置化 CORS。

本地开发示例：

```text
CORS_ORIGINS=http://localhost:5173
```

后端必须满足：

- 允许配置中的前端 Origin；
- 正确处理 `OPTIONS` 预检请求；
- 允许 `Content-Type` 和 `Authorization` 请求头；
- 允许 `GET`、`POST`、`DELETE` 和 `OPTIONS` 方法；
- 不建议在生产配置中无条件允许所有 Origin；
- 如果使用 cookie 保存登录状态，还必须正确配置 credentials；本项目默认使用 Bearer token，因此不要求 cookie 鉴权。

## 10. 数据模型要求

后端至少需要持久化以下信息。

### 10.1 用户表

| 字段 | 说明 |
|---|---|
| `id` | 用户唯一 ID |
| `username` | 唯一用户名 |
| `password_hash` | bcrypt 等算法生成的密码哈希 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间，可选 |

禁止保存：

- 用户密码明文；
- 固定测试密码；
- 写死的 token。

### 10.2 短链接表

| 字段 | 说明 |
|---|---|
| `id` | 短链接唯一 ID |
| `user_id` | 所属用户 ID |
| `code` | 唯一短码 |
| `original_url` | 原始 URL |
| `click_count` | 点击次数 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间，可选 |

必须建立或保证以下约束：

- `users.username` 唯一；
- `links.code` 唯一；
- `links.user_id` 指向所属用户；
- 查询用户数据时始终使用 `user_id` 过滤。

## 11. 安全要求

以下内容是基础版本的硬性要求：

- 密码必须使用 bcrypt 等安全算法哈希后存储；
- 密码不能出现在日志、响应和错误信息中；
- token、JWT secret、数据库密码不能硬编码；
- 需要鉴权的接口必须验证 token；
- 所有用户资源必须做数据归属校验；
- 原始 URL 只允许 `http` 和 `https` 协议；
- SQL 必须使用 ORM 参数绑定或预编译参数，禁止拼接用户输入；
- 服务端错误响应不能直接泄露数据库 SQL、文件路径或密钥；
- 应对请求 JSON、用户名、密码和 URL 做长度限制；
- 生产环境不应记录完整的 Authorization 请求头。

---

## 12. 最低测试要求

项目至少应包含自动化测试。只测试一个永远成功的工具函数不算完整验收测试。

最低要求覆盖以下场景：

1. 注册成功，数据库中密码不是明文。
2. 重复用户名注册返回 `409`。
3. 正确账号密码登录成功并返回 token。
4. 错误密码登录返回 `401`。
5. 不带 token 创建短链接返回 `401`。
6. 带有效 token 创建短链接成功。
7. 用户 A 查询不到用户 B 的短链接。
8. 短链接访问返回 `302`，并且点击数增加。
9. 配额设置为 `2` 时，第 3 次成功创建被拒绝并返回 `429`。
10. 服务重启后用户和短链接数据仍然存在。

推荐使用 `httptest` 编写接口级测试，避免只测试内部函数而没有验证真实 HTTP 行为。

## 13. 联调验收流程

前端和后端按照以下顺序进行联调：

1. 启动后端，访问 `GET /health`，确认返回 `{"status":"ok"}`。
2. 前端打开注册页面，调用注册接口。
3. 注册成功后跳转到登录页面。
4. 登录成功后把 token 保存在前端状态或本地存储中。
5. 前端请求短链接列表时携带 Bearer token。
6. 创建短链接并显示返回的 `short_url`。
7. 点击“访问短链接”，通过浏览器跳转到原始 URL。
8. 回到列表页，确认 `click_count` 已增加。
9. 修改后端 `DAILY_LINK_QUOTA=2` 并重启。
10. 同一个账号创建第 3 条短链接，前端显示配额错误。
11. 创建另一个账号，确认看不到第一个账号的短链接。
12. 停止并重新启动后端，确认之前的数据仍然存在。

## 14. 扩展功能

以下功能不属于基础版本，不得作为基础接口验收的前置条件：

- API Key 和第三方创建接口；
- 每分钟请求限流；
- 短链接过期时间；
- 自定义短码；
- 统计报表；
- Docker 打包；
- Redis 缓存；
- OpenAPI/Swagger 自动文档。

如果实现 API Key，必须满足：

- API Key 不能明文存储；
- API Key 只能在创建成功时完整展示一次，或提供安全的重新生成机制；
- API Key 可以撤销；
- API Key 和登录 token 的使用方式必须在项目 README 中单独说明；
- 扩展功能不能破坏本文档规定的基础接口。
